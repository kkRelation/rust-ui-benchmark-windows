# KAS Probe Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add and measure a KAS 0.17/WGPU resident probe, retaining reproducible source/results while removing its isolated caches afterward.

**Architecture:** A single KAS Runner owns application data containing the selected row and two Window roots. Commands enter through a channel and are applied on the KAS event context; both widget trees read the same application data. KAS's exposed Winit window access toggles visibility when possible, with the audited title/PID-scoped Win32 adapter as the only fallback.

**Tech Stack:** Rust 2024, KAS 0.17 desktop/WGPU crates, shared `ui-bench-protocol`.

**Spec:** `docs/superpowers/specs/2026-10-29-sequential-framework-expansion-design.md`

## Global Constraints

- Requires completed foundation, Iced, and gpui-kit plans.
- Exact two-window protocol, titles, sizes, 72 rows, 66 keys, and shared 400x20 ms workload.
- Use KAS's normal WGPU desktop backend; no renderer fallback or custom frame loop.
- Pin every direct KAS crate to 0.17.0 and commit the lockfile.
- Work only in `.benchmark-work/kas` and clean it only after successful validation.
- Validate, commit, run `git swap auto`, push, and confirm local/remote equality after every completed task.

## Review Focus

- Both KAS windows must share top-level `BenchData`, not duplicate per-window counters; Task 1 unit-tests shared updates.
- The command channel must wake the KAS event loop while hidden; Task 1 tests the bridge abstraction and Task 3 exercises hidden workload control.
- WGPU must remain the active backend; Task 3 records the resolved/render metadata.
- Runtime visibility must retain native windows rather than close/recreate them; Task 3 compares handles/topology across checkpoints.
- KAS's partial IME/accessibility status is irrelevant to this reduced scene and must not introduce alternative widgets/workload; scene review in Task 1 checks parity.
